# 0004 — Data snapshots are an identity axis of their own

- Status: accepted
- Date: 2026-09-19

## Context

ADR 0003 binds facts about the binary to an identified build of `Extensions.dll`. That
covers layouts and symbols, and it silently assumes the client's *data* is a constant.

It is not. On 2026-09-19 a second DBC set arrived (`cointhrow-2026-09-09`, an unannotated
upload) and was compared with the set extracted from our own lab client
(`ascension-live-2026-09-17`). Every table has the same `fieldCount` and `recordSize` —
no schema differs — yet 64 of 368 tables differ in content, and `CharacterAdvancement.dbc`
alone has 4 ids present only in one set and 25 present only in the other.

So a statement like "entry 17567 exists" is true of a snapshot, not of "the client". A
fiche that grades such a statement `L2` without saying which catalogue it read is not
reproducible, which is the same defect ADR 0003 fixes for addresses.

There is a second reason. The CoA fork is a reconstruction: its own silence about an
entry is not evidence that the entry never existed. One catalogue cannot distinguish
"absent from the game" from "absent from this dump". Two independent catalogues can, and
the measured id deltas give the noise floor for that judgement.

## Decision

- Data snapshots are registered in `client/datasets.yaml` with an id, provenance, an
  evidence level of their own, and a pointer to a per-table fingerprint manifest under
  `client/datasets/`.
- Manifests are generated by `tools/extract/dbcinfo.py manifest`, never hand-written.
- A fiche may declare `client_datasets:`; when any of its graded items sits at `L2`
  (read from client source), declaring it is **required** and the linter enforces it.
- Comparisons between snapshots are recorded under `client/datasets/deltas/`, each
  stating the commands that reproduce it.
- DBC files themselves are never committed. Only fingerprints and measurements.

## Options considered

- **Ignore it and treat the client as one thing.** What ADR 0003 implied. Cheap until a
  catalogue-derived fact silently stops being true, which is unfalsifiable after the fact.
- **Fold the data snapshot into the build id.** Fewer concepts, but wrong: the same
  binary serves many catalogue versions, and conflating them forces a fake build entry
  every time data moves.
- **Commit the DBC set so facts are self-contained.** Reproducible, and 773 MB of
  redistributable game assets per snapshot. Refused on both size and the no-assets rule.
- **A separate axis, fingerprinted not stored.** Chosen.

## Consequences

- Two axes to pin instead of one. Fiches get an extra field; the linter only demands it
  where it matters.
- Snapshot manifests are large generated files (368 entries each). They diff badly but
  are never read by hand, and they make "which catalogue said that" answerable.
- Comparing snapshots needs the sets on disk. They stay outside the repository, so a
  delta report cannot be regenerated by someone who does not hold both — hence the
  requirement that each delta states its commands and its measurements in full.
- `tools/extract/dbcinfo.py columns` resolves differing columns as string offsets to
  separate a repacked string block from real content change. It cannot know which columns
  are string references; on a numeric column the result is nonsense. The tool says so, and
  delta reports state which columns were left unexamined for that reason.
