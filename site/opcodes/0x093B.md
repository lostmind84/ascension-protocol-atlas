# `0x093B` SMSG_PATCH_CHR_CLASSES

**server to client** · status `hypothetical` · evidence `L1` · layout `named` · client code `handler`

Fiche: [`protocol/opcodes/0x093b-smsg-patch-chr-classes.yaml`](../../protocol/opcodes/0x093b-smsg-patch-chr-classes.yaml)

One row of the stock ChrClasses.dbc (AzerothCore already loads this table; ADR 0005), read by the handler at RVA 0x0022ab90 as 7 individuated dwords then 5 lpstrings. ClassID (leading, the universal 'n' convention for these tables, and ChrClassesEntry's own first column) is named from DBCStructure.h (L1). The other 6 numeric reads and 5 strings do not reconcile with ChrClassesEntry: only 4 more numeric columns are active (powerType, spellfamily, CinematicSequence, expansion) against 6 observed, and the file has 3 locale-string blocks (name, kept; nameFemale and nameNeutralGender, both commented out) against 5 lpstrings on the wire, so nothing past ClassID is named here. Read against the real decompiled handler (build/ghidra/handlers-c/0x093b.c): confirms the 7-dwords-then-5-strings shape exactly (a clean sequential read, no branching), but the mismatch is real, not a coarse-trace artifact -- ChrClassesEntryfmt's prefix before the name[16] block is only 4 columns (ClassID, an unused column, powerType, another unused column), so at least 3 of these 7 reads land on bytes the file format calls part of the name locale block, read here as plain dwords rather than through the string helper. The simplest explanation is that AzerothCore's own ChrClassesEntry (written for the server's needs) keeps fewer columns than the client's own internal consumer of this table actually reads off the wire -- DBCStructure.h describes the file, not what any given client-side reader does with it, and this function is graphic proof that the two can diverge. Not enough to name any individual field past ClassID.
