# `0x0726` SMSG_CHARACTER_ADVANCEMENT_KNOWN_ENTRIES

**server to client** · status `hypothetical` · evidence `L1` · layout `named` · client code `none`

Fiche: [`protocol/opcodes/0x0726-smsg-character-advancement-known-entries.yaml`](../../protocol/opcodes/0x0726-smsg-character-advancement-known-entries.yaml)

The complete set of Character Advancement entries the character holds. The client diffs it against its own container, fires ASCENSION_KNOWN_ENTRY_UPDATED / _REMOVED, and answers C_CharacterAdvancement.IsKnownID and GetTalentRankByID from it. Always the full set, never a delta.

## Layout

| field | type | evidence | notes |
| --- | --- | --- | --- |
| `count` | `u32` | L5 | The packet carries the COMPLETE set and replaces the client's container. Proven: count=0 clears it and IsKnownID goes false for an entry that was known a moment before. The capture reference reports a login burst of twelve 0x0726 in one session, the first eleven with count = 1..11 and then a full eleven-record set in a different order, for payload sizes of 25 to 235 bytes. 4 + 21*1 = 25 and 4 + 21*11 = 235 exactly, so their sizes confirm this count and the 21-byte record below with nothing trailing it. A growing series is not a delta protocol: each packet is complete as of its moment, which is what this field means.
 |
| *repeat × count* | | | |
| &nbsp;&nbsp;`entryId` | `u32` | L5 | CharacterAdvancement.dbc entry id. PRESENCE IN THE SET is what makes IsKnownID(entryId) answer true -- no other field is required.
 |
| &nbsp;&nbsp;`rank` | `u32` | L3 | THE RANK, by shape. Decompiled: the advancement service's rank getter (RVA 0x00152920) walks a vector with stride 0x20, matches the key at record +0x04 and returns record +0x08 -- exactly where this field lands. An earlier note here said the opposite, reasoning from #4128's unverified claim that the rank is read at +0x14; the normal path never reads +0x14. The lab's 0 is explained and is NOT a packet problem: three accessors read one vector keyed at +0x04 -- membership, this rank at +0x08, and the lock byte at +0x10. IsLockedID matched the raw entry id in the very same forged record, so the record is stored and keyed correctly. GetTalentRankByID is the only accessor RESOLVED. The rank is stored here correctly; the client cannot read it back. GetTalentRankByID first consults the WILDCARD store (0x2c records, filled by SMSG_WILDCARD_ENTRY_LEARNED 0x0621), which is empty outside that game mode, then falls back to this store keyed on *(catalogue_entry + 0) -- not the entry id, so it never matches. Proven by one forged record: u8=1 made IsLockedID true, which requires +0x04 == 31194 in this very vector, while +0x08=5 still read back as 0. A client defect, not a packet or server one. See client/symbols/.../rank-source.md. The capture reference reports rank = 1 in every record of its sample, which is consistent but proves nothing about which offset the client reads back.
 |
| &nbsp;&nbsp;`marker` | `u32` | L1 | Third-party claim (#4128): 2 on automatic/implicit nodes, 1 elsewhere. Shipped as 0 by #4027. Sent as 0, 1 and 2 with no observable effect on IsKnownID, IsLockedID, IsTalentID or GetTalentRankByID. Whatever it selects, it is not any of those. The capture reference reports this u32 as the constant 1 in every record of a real login burst. That is COMPATIBLE with the lab, not a contradiction: the lab showed only that 0, 1 and 2 leave those four predicates unchanged, which says nothing about what a live server chose to send. Taken together the two readings say a real server sends 1 for ordinary entries, #4128 says 2 for automatic ones, and no client predicate we have queried can tell the difference. The consumer that distinguishes them has still not been found -- that is the open question, and it is unchanged.
 |
| &nbsp;&nbsp;`flag` | `u8` | L5 | THIS IS A LOCK FLAG, NOT A KNOWN GATE. Proven on a real client: 0 leaves the entry unlocked, and 1, 2 and 255 all make IsLockedID(entry) answer true, while IsKnownID stays true in every case. #4128's reading -- that IsKnownID requires this byte to be 1 -- does not hold here. A locked entry is one the UI refuses to interact with, which looks like "the entry did not work" without being the same thing; that is very likely what was observed in game. The capture reference, by the same author as #4128, reports this byte as the constant 0 in every record of a live capture. A live server therefore sent 0 on entries the client plainly treated as known, which is what the lab proves and the opposite of what #4128 concluded. #4128's gate reading should be considered withdrawn by its own author's capture.
 |
| &nbsp;&nbsp;`buildTime` | `u32` | L1 | Name from #4128. Shipped as 0 by #4027, and forging it has never been tested. The capture reference calls it a content/build timestamp and reports the single value 0x6A501487 in every record of its sample. Read as a little-endian u32 Unix timestamp that is 1783633031 = 2026-07-09 21:37:11 UTC; the reference's own parenthetical says 2026-07-06, so their value and their date disagree by three days and we cannot tell which they meant. What survives that discrepancy is the shape: one value, identical across every record of one session, in the plausible range for a 2026 epoch second. That reads like a per-content-build stamp rather than anything per-entry -- but it is their capture, not ours, and no consumer of this field has been found in the binary. Still L1.
 |
| &nbsp;&nbsp;`reserved` | `u32` | L1 | Observed 0 in every source, the capture reference included, which reports it as a constant 0 across a live session. Never forged, and no read of it has been found. Its presence, rather than its value, is what the reference's 21-byte record and its 4 + 21n payload sizes confirm: there is a sixth field and nothing after it.
 |
