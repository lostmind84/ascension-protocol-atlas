# `0x0939` SMSG_PATCH_AREA_TABLE

**server to client** · status `hypothetical` · evidence `L1` · layout `named` · client code `handler`

Fiche: [`protocol/opcodes/0x0939-smsg-patch-area-table.yaml`](../../protocol/opcodes/0x0939-smsg-patch-area-table.yaml)

One row of the stock AreaTable.dbc (AzerothCore already loads this table; ADR 0005). Reading the actual decompiled handler (build/ghidra/handlers-c/0x0939.c, RVA 0x0022a560) by hand fully resolves this record, which an earlier pass had left mostly unnamed: 12 sequential dwords (ID, mapid, zone, exploreFlag, flags, 5 uncommented columns, area_level) then a 4-dword loop then 3 more sequential dwords -- 19 numeric reads total, exactly the file's 11 pre-string columns (0-10) plus its 8 post-string columns (28-35: team, LiquidTypeOverride[4], and 3 genuinely undocumented trailing columns) -- then a single lpstring for area_name (columns 11-27, collapsed). The wire gathers every non-string column first, in file order within each of the two groups, and reads the one string last, even though it sits between those two groups in the file itself. 19 + 17 (collapsed) = 36, the file's full column count, with nothing left over -- resolving the earlier apparent 14-vs-19 shortfall, which was an artifact of a coarser trace merging some of these reads. 11 of 20 fields are named from DBCStructure.h (L1); the 5 file-commented 'unused' columns and the 3 wholly-undocumented trailing ones are core 'x' columns, identified with confidence but kept unnamed per that convention.
