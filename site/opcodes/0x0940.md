One row of the stock DungeonEncounter.dbc (AzerothCore already loads this table; ADR 0005), read by the handler at RVA 0x0022bcc0 as 6 dwords then 1 lpstring. id (leading, the universal 'n' convention, and DungeonEncounterEntry's own first column) and encounterName (the file's only locale-string block, encounterName[16], and the only string-type candidate) are named from DBCStructure.h (L1). The 5 numeric fields in between do not reconcile: DungeonEncounterEntry names only 3 more active columns (mapId, difficulty, encounterIndex; orderIndex is commented out) against 5 observed reads, so none of them is individually named here. Read against the real decompiled handler (build/ghidra/handlers-c/0x0940.c): confirms a clean sequential 6-dwords-then-1-lpstring shape (no branching), and shows the string is read before the 6th dword is stored into the final record, so that dword is not simply "the last of the prefix" -- it is stored at a position after the string, suggesting a value from past encounterName's own column range (col5-20) rather than an extra prefix column. Column arithmetic doesn't close cleanly enough to name it (the file has 23 columns total: id/mapId/difficulty/orderIndex(x)/encounterIndex/encounterName[16]/ nameFlags(x)/spellIconID(x) -- 7 non-string columns against the 6 observed, off by one), so it stays unnamed.
