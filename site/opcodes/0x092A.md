# `0x092A` SMSG_PATCH_SPELL

**server to client** · status `unknown` · evidence `L3` · layout `widths` · client code `handler`

Fiche: [`protocol/opcodes/0x092a-smsg-patch-spell.yaml`](../../protocol/opcodes/0x092a-smsg-patch-spell.yaml)

Named SMSG_PATCH_SPELL by the client's own opcode table. One row of the stock Spell.dbc (AzerothCore already loads this table; ADR 0005), sent as an opaque 680-byte blob (RVA 0x00231de0, no per-field split available) followed by 4 lpstrings. Spell.dbc's own file has exactly 4 locale-string blocks (SpellName, Rank, Description, ToolTip -- the last two fully commented out of SpellEntry) and 234 columns total; the numeric arithmetic closes exactly (234 - 4x16 string slots = 170 dwords = 680 bytes, matching the blob), which is a stronger reconciliation than most opcodes in this bucket get. Even so, this fiche does not decompose the 680-byte blob into named columns or the 4 lpstrings into SpellName/Rank/Description/ToolTip: the blob is a single un-individuated read, so nothing establishes that the internal byte order was not reshuffled during packing even though the total closes, and a sibling table (SkillLine, 0x0933) that looks structurally identical has a string-block count that does NOT reconcile with its lpstring count (3 vs 4), which is direct evidence that this project's assumption "one lpstring per locale block, in file order" fails at least once and should not be trusted anywhere it is not independently confirmed. DBCStructure.h (SpellEntry) and DBCfmt.h (SpellEntryfmt) were checked; no naming source safe enough to assert per-field was found. Read against the real decompiled handler (build/ghidra/handlers-c/0x092a.c): confirms the blob is one 170-dword (0xaa) copy loop and the 4 strings are 4 separate, sequential FUN_100d3680 calls in a fixed order -- consistent with, and no stronger than, the structure already in this layout. The same function also inspects and conditionally rewrites 3 pairs of fields after the copy (comparing one member of each pair against 0x6b/0x6c and the other against 30), a plausible fit for 3 of SpellEntry's MAX_SPELL_EFFECTS arrays, but Ghidra's declared locals for that logic do not reliably map to fixed byte offsets inside the 680-byte blob (the copy loop's destination array is declared shorter than the copy itself and spills into adjacent locals in a way this pass could not safely resolve to specific columns), so nothing further is asserted from it.
