One row of the stock LFGDungeons.dbc (AzerothCore already loads this table; ADR 0005). Reading the actual decompiled handler (build/ghidra/handlers-c/0x0945.c, RVA 0x0022e590) by hand fully resolves this record, which an earlier pass had left mostly unnamed: 14 sequential dwords (ID, then 13 of columns 18-31) then 3 lpstrings. The wire gathers every non-string column first, in file order, skipping past the file's 3 string-type columns (Name[16] at column 1, the standalone TextureFilename at column 28, and Description[16] at column 32) and reading them last, in the same file order. 14 + 17 (Name, collapsed) + 1 (TextureFilename) + 17 (Description, collapsed) = 49, the file's full column count, with nothing left over -- this also resolves the earlier '2 file blocks vs 3 lpstrings' mismatch: TextureFilename is a genuine third string column the first naming pass had not counted. 13 of 17 fields are named from DBCStructure.h (L1); Faction, OrderIndex, TextureFilename and Description are core 'x' columns, identified with confidence but kept unnamed per that convention.
