# `0x093A` SMSG_PATCH_CHAR_START_OUTFIT

**server to client** · status `hypothetical` · evidence `L1` · layout `named` · client code `handler`

Fiche: [`protocol/opcodes/0x093a-smsg-patch-char-start-outfit.yaml`](../../protocol/opcodes/0x093a-smsg-patch-char-start-outfit.yaml)

One row of the stock CharStartOutfit.dbc (AzerothCore already loads this table; ADR 0005). Reading the actual decompiled handler (build/ghidra/handlers-c/0x093a.c, RVA 0x0022aa60) by hand resolves the earlier concern that this fiche's evidence looked incomplete: the record is sent IN FULL, all 77 columns, in three chunks -- ID + Race/Class/Gender/outfitID (5 dwords, cols 0-4) + a 24-dword loop (ItemId, cols 5-28) + a second 24-dword loop (ItemDisplayId, cols 29-52) + a third 24-dword loop (ItemInventorySlot, cols 53-76). A genuinely non-obvious finding: even though CharStartOutfitEntryfmt marks Race/Class/Gender/outfitID as 1-byte columns ('b'/'X') in the FILE's own on-disk record, the WIRE sends a full 4-byte dword for each of them (confirmed by the buffer position advancing by 4 each time) with only the low byte kept. ItemDisplayId and ItemInventorySlot are also sent in full even though CharStartOutfitEntry comments them out entirely ("not required at server side") -- AzerothCore's struct not keeping a column is not evidence the wire omits it. ID, Race, Class, Gender and ItemId are named from DBCStructure.h (L1); outfitID/ItemDisplayId/ItemInventorySlot are core 'x'/'X' columns, identified with confidence but kept as unnamed fields per that convention.
