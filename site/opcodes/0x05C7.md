# `0x05C7` SMSG_CHALLENGE_QUERY_COMPLETION_RESPONSE

**server to client** · status `hypothetical` · evidence `L3` · layout `named` · client code `handler`

Fiche: [`protocol/opcodes/0x05c7-smsg-challenge-query-completion-response.yaml`](../../protocol/opcodes/0x05c7-smsg-challenge-query-completion-response.yaml)

The CoA server calls it `SMSG_COA_CHALLENGE_COMPLETION_LIST`.

The trial leaderboard: a challengeID, a level, a count and that many completion records. Each record independently repeats the challengeID and level, then a player name, a start time and a complete time (each padded to 8 bytes, high dword always zero) and three more strings (race, gender, class), all four strings length-prefixed with no NUL. Read from the handler at 0x001376b0, its record parser at 0x0013efd0 and, for record field names, the Lua-table converter at 0x0013bf30 (all decompiled, DecompAt.java; the handler and parser 2026-09-20 under GHIDRA_WORKSPACE=unclassified, the converter re-decompiled and its callers checked 2026-09-20 under GHIDRA_WORKSPACE=verify-unclassified). Skeptic correction: the converter is not called by the packet handler's per-record loop -- `Callers.java` finds exactly one caller of 0x0013bf30, `FUN_10140ab0`, a distinct function with no reference anywhere in the SMSG 0x05C7 handler or its parser. The loop instead calls a generic, 86-caller helper (`FUN_1013b8b0`) after each parse. What the loop actually builds is a 0x78-byte-strided C++ struct vector; `FUN_10140ab0` walks that same stride over a vector and calls the converter on each element -- almost certainly a Lua-facing getter invoked later, on demand, not during packet receipt. The record field *names* still stand, because the offsets the converter reads (0, 1, 2-7, 8, 10, 0xc-0x11, 0x12-0x17, 0x18-0x1d) line up exactly with the offsets the parser writes -- re-verified independently below -- but the claim that the handler calls the converter per record does not survive and is corrected.
