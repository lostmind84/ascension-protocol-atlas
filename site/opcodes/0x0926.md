# `0x0926` SMSG_CA_AVAILABLE_CREDITS_UPDATE

**server to client** · status `proven` · evidence `L5` · layout `proven` · client code `handler`

Fiche: [`protocol/opcodes/0x0926-smsg-ca-available-credits-update.yaml`](../../protocol/opcodes/0x0926-smsg-ca-available-credits-update.yaml)

A credit balance the Character Advancement UI spends (ability and talent unlearns, per CharacterAdvancementCostUtil.lua): one u8 credit type and its u32 amount, stored in the client's credits map keyed by the type. The Lua read is CA_GetCreditAmount(type) by name; that binding's body was not followed to the same map here.

## Layout

| field | type | evidence | notes |
| --- | --- | --- | --- |
| `creditType` | `u8` | L5 | The key of the client's credits map; forged 1 -> CA_GetCreditAmount(1) changed, other types did not. The client names the four values itself: Enum.ResetCreditType = {AbilityReset = 1, TalentReset = 2, AbilityUnlearn = 3, TalentUnlearn = 4} (Interface/SharedXML/Enum.lua:275, corpus ascension-ui-patch-b-stock, L2), and CharacterAdvancementCostUtil.lua passes exactly those constants to CA_GetCreditAmount. So 1 and 2 count resets, 3 and 4 count unlearns, ability and talent respectively. The capture reference independently reports the range as 1-4 naming the same enum, with a live sample of 1 -> 0, 2 -> 0, 3 -> 2, 4 -> 3 (L1); the enum itself we read here, so the naming is L2, not L1.
 |
| `amount` | `u32` | L5 | Forged 777 -> CA_GetCreditAmount(1) answered 777 (was 0). The UI divides the gold part of a reset cost by this counter (CharacterAdvancementCostUtil.lua:99, CalculateResetCostGold(level, CA_GetCreditAmount(resetCreditType))), so the value scales what a reset costs.
 |
