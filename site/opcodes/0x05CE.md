# `0x05CE` SMSG_TRANSMOG_COMPONENT_UPDATE

**server to client** · status `hypothetical` · evidence `L3` · layout `empty` · client code `none`

Fiche: [`protocol/opcodes/0x05ce-smsg-transmog-component-update.yaml`](../../protocol/opcodes/0x05ce-smsg-transmog-component-update.yaml)

Named SMSG_TRANSMOG_COMPONENT_UPDATE by the client's own opcode table, sitting right after CMSG_TRANSMOG_COMPONENT_APPLY (0x05cd) and before SMSG_TRANSMOG_COMPONENT_SUCCESS (0x05d1, with two unnamed opcodes 0x05cf/0x05d0 between them) -- the natural reading is a server push of a changed component followed by a success ack for the apply, but nothing in this build has code to send either half of that: the client registers no handler for 0x05ce. The registration scan (`handlers.yaml`) is exhaustive over every static `push handler; push opcode; call <registrar>` site across all three registrars Extensions.dll uses (532 total registrations, including the far-higher 0x09bf in an unrelated family -- see that fiche), so the usual "Extensions.dll-only" caveat for a *standard* opcode (client/symbols/.../handlers.md) does not apply here: 0x05ce is outside AzerothCore's baseline entirely (protocol/known-baseline.yaml), so stock Ascension.exe code has no notion of it either -- there is nowhere else a handler could live.
